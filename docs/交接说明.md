### 4.2 出包（**Day 27 起只跑一条命令**；下面 5 步是它的原理）

```powershell
cd D:\Document\Project\vibe-coding-project-app
npm run ship            # debug 包（本地冒烟）
npm run ship:release    # 正式签名包（要交付 / 要能长期升级的）
```

`scripts/ship.js` 一次做完 5 步，**任一步失败立即非 0 退出**，并打印每步耗时、产物路径与 sha256：

| 步 | 原手工命令 | 现在由 ship.js 做 |
|---|---|---|
| ① | `cd web2; npx vite build` | 跑 `npm run build`，校验 `dist/index.html` 存在且时间新鲜 |
| ② | 壳仓 `npm run sync` + `npm run patch-android` | 同，并校验 `www/index.html` 存在 |
| ③ | `JAVA_HOME=<JDK21>; gradlew --stop; gradlew assembleDebug` | 同（JDK 21 由脚本显式注入，**不依赖系统 JAVA_HOME**）；跑之前**先删上一轮 apk** |
| ④ | `Copy-Item ... dist-apk\schedule-v<版本>-<日期>.apk` | 自动命名归档 + 大小比对 + sha256 |
| ⑤ | `python web2/tmp/verify-apk.py <apk> v<版本>` | 同（`PYTHONIOENCODING=utf-8` 由脚本注入） |

**为什么必须收成一条**：原来 ④ 是独立的一条 `Copy-Item`，gradle 失败时它照跑，会把**上一次的旧包**改名归档成新版本（2026-10-03 真踩过，差点交出假包）。现在 ③ 失败即在 ③ 停下，且跑前先删旧产物、跑后校验文件确实存在，交假包这条路被堵死。

**失败时会怎样**（都是非 0 退出，后续步骤一律不跑）：

- 主项目 / `android/` / JDK 21 路径不存在 → 步骤 ① 体检直接退出（路径不同用 `SHIP_SRC_ROOT` / `SHIP_JAVA_HOME` 覆盖）
- `--release` 但缺 `android/key.properties` → 直接退出（**不静默退回 debug 签名**，那会出个假的 release 包）
- gradle 非 0 → 停在 ③
- gradle 退出 0 但产物不存在 → 停在 ③（这正是「交假包」的成因）
- release 包签名是 `CN=Android Debug` → 停在 ③ 报「这是个假 release 包」
- 找不到 python → 停在 ⑤（本机 PATH 上的 `python` 是 Microsoft Store 占位符，脚本会自动改用 `py -3`）

**验证口径**（脚本已内置，看结论行即可）：`dist vs APK = 一致 ｜ dist vs www = 一致 ｜ 版本串 = 命中`。

**脚本参数**：`--release` / `--skip-web-build` / `--skip-verify` / `--out=<文件名>` / `--keep-apk` / `--help`。

**实测记录（2026-10-07）**：debug 全链 20.0s → `dist-apk\schedule-v1.42.2-20261007-debug.apk`（37,484,194 B，sha256 `948d643c…`）；release 全链 31.8s → `dist-apk\schedule-v1.42.2-20261007-release.apk`（36,419,684 B，sha256 `5e5a91bb…`，签名 `CN=Schedule Assistant` / 证书 SHA-256 `1420dda8…`）；两个失败用例（主项目路径不存在、JDK 21 路径不存在）都正确非 0 退出。**npm run ship 自己出 debug 包时曾因 python 探测的 `-c` 参数没加引号而误判「没有 python」，已修**（改用 `spawnSync` 数组传参，绕开 shell 转义）。

## 8. 和这位用户协作的纪律（照 `AGENTS.md`，很容易踩）

1. **一天一份清单**：用户把当天的任务清单整块发来，那就是唯一范围；清单外的「顺手优化」先问，别自己动手。
2. **一次只做一个步骤**：做完停下，报告「做了什么 / 改了哪些文件 / 怎么验证（用户能亲眼确认的结果）」，然后**等用户说「进入下一板块」**，不要连做。
3. **人机分工**：要用户手动做的（注册、点按钮、装软件、截图）不要替他做，也不要假装完成；只讲清步骤、预期现象和坑，然后停下等。
4. **要用户拍板**：选方案/起名字/定风格，列选项和代价让他选。
5. **讲清楚**：每步用「做了什么 → 结果 → 为什么」；不懂的概念一两句话解释；报错先说清错在哪、原因、打算怎么修，等他同意再动手。
6. **页面一变就截图给他看**（用户多次强调的硬要求）：用 878 宽预览读图后再决定点击坐标，或直接给他 PNG。
7. **Git**：提交前先列文件清单确认；信息 `Day X｜一句话说明`；回退只用 `git revert`（保留历史），**禁止** `git reset --hard` 和强推。
8. **反复失败就停**：同一个操作连着失败，停下报告「试了什么 / 报什么错 / 判断原因」，不要循环重试。
