# 协作提速约定

> 立此文档的原因：本会话统计出「七成时间花在工具调用上」，逐项查清后把能省的部分固化下来。
> 写于 2026-10-15（Day 30 收尾后）。数字都是本机实测值，不是估计。

## 一、已落进流程的（现状，不是提案）

| 约定 | 状态 | 说明 |

| 开工先报预估 | 已生效 | 四段式：几步/几个文件 → 几分钟 → 能否后台并行 → 最坏情况；估到 ≥15 分钟先问是否拆小 |

## 二、新约定（下次开工照做）

1. **受影响的脚本一律并发跑**，不再一个一个来 —— 14 个脚本 7 分钟可压到 2~3 分钟。
2. **互不相干的文件编辑合并到同一步发出**，不来回等。
3. **文档同步并行做** —— 这是历史上最容易超时的一项，4~6 份之间没有依赖。
4. **独立调研类任务（≥3 个方向）默认派子代理并行**，主进程只负责汇总与拍板。

## 三、不能并行的（有硬依赖，写下来免得反复问）

- 手势 / 物理类脚本：抢 CPU 会让「快甩 ≥18 格」这类贴阈值测量抖红，已强制串行。
- 构建 → 部署 → 验证：后一步要读前一步的产物。
- 同一个文件的多次编辑：会互相覆盖。
- 提交推送：必须等全部改动落盘（但本身只要 1 分钟）。
- 主进程的判断：读结果、定下一步永远只能一个人在想。

## 四、总账（实测锚点）

| 动作 | 耗时 |
| --- | --- |
| 全档发布前检查 `verify.mjs` | ≈12 分钟 |
| 单脚本回归 | 20~60 秒（手势/物理类最慢） |
| 出包 `npm run ship` | ≈28 秒 |
| 公网静态托管部署 | ≈30 秒 |
| 提交并推送 | ≈1 分钟 |
| 文档同步（4~6 份） | 5~15 分钟（最易超时） |

**省下来的账**：脚本并发 → 省 4~5 分钟；文档并行 → 省 3~8 分钟；子代理调研 → 把「先花两小时调研」压到 5 分钟。

## 五、比并行更省时间的一条

**「猜你想要什么」是最贵的动作。** 历史上的返工（文案瘦身反复、截图重拍）都不是执行慢，而是方向没先对齐。
所以默认动作是：**歧义超过一个选项就先问一句**，而不是先做一版再改。

## 六、子代理并行的限制

- 子代理不共享主会话上下文，指令必须完整自述。
- 不能有两个子代理同时改同一个文件。
- 更费额度 ⇒ 只用于调研和独立模块，不用于改同一批源文件。
