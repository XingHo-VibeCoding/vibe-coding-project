# 回滚手册

> 出事时先翻这份。目标：**用最短的路把线上/仓库弄回一个能用的状态**。
> 首次演练：**2026-10-12** ｜ 本手册对应的发布：**v1.0**（提交 `574a8a3`，标签 `v1.0`）
> 演练实测耗时：**发坏版本 5.2s ｜ 回退到 v1.0 5.3s ｜ 全程 18.3s**（静态托管路径）

## 0. 三十秒判断：现在该走哪条路

先问自己一句：**「坏掉的是什么？」**

| 坏掉的东西 | 走哪一节 | 大概多久 |
|---|---|---|
| 公网页面（打不开 / 白屏 / 点不动） | §2 静态托管回退 | **≈ 20 秒** |
| 刚提交的代码（还没发，或发了要撤） | §3 Git 回退 | ≈ 1 分钟 |
| 云函数（接口 500 / 报错） | §4 云函数回退 | 5–15 分钟 |
| 云端数据（被覆盖 / 写坏） | §5 数据恢复 | 看严重程度 |
| 手机 App | §6 App 回退 | ≈ 2 分钟 |

**顺序原则**：先止血（让线上可用）→ 再查因 → 最后补记录。

## 1. 「什么情况必须回滚」判断表

回滚是**止损**，不是**修复**。下面这张表帮你决定「马上退」还是「先看看」。

| 现象 | 判断 | 动作 |
|---|---|---|
| 公网打不开 / 一直白屏 | **必须立刻回滚** | §2，先退到上一版再查 |
| 页面能开但核心功能坏了（加不了日程、课表空了） | **必须立刻回滚** | §2 |
| 只是样式错位 / 文案错别字 | 可以**不用退** | 正常修，下次发布带上 |
| 刚 push 了一个提交，CI/自检红了 | **回滚那个提交** | §3，用 `git revert` |
| 云函数返回 500 且**所有**请求都失败 | **必须回滚** | §4 |
| 云函数偶发失败（重试就好） | 先观察 | 记下来，不一定回滚 |
| 云端数据被覆盖成错的 | **必须恢复** | §5 |
| App 装完就崩 | **回滚到上一个包** | §6 |

**别回滚的情况**（避免瞎折腾）：
- 只有你一个人遇到的、刷新就好的问题（多半是 CDN 缓存）；
- 已经在修、且影响面很小的功能缺陷（回滚会让修复白做）；
- 你**还没确认**坏的是什么（先确认再动，盲退可能把好版本也弄丢）。

## 2. 静态托管回退（最主要的路径，≈20 秒）

**前置**：你有一份「正确版本」的归档，在 `release-archive/<版本>/`（**当前最新是 `release-archive/v1.1/`**，2026-10-13 深夜建立，含三个 bug 修复 + 原生控件清零；v1.0 是更早的里程碑，**回退别用它**，会把已修的 bug 带回来）。
**没有归档怎么办？** 从 git 历史重建：`git checkout <那次发布的提交> -- web2` → 重新 `vite build` → 得到 dist。

### 步骤

```bash
cd D:/Document/Project/vibe-coding-project
E=vibecoding-test-d5fqmhbb955e19dd

# 1) 重传归档好的正确版本（--safe 会先备份当前坏版本，方便你事后回看）
tcb hosting deploy ./release-archive/v1.1 app -e $E --safe --verify

# 2) 立刻验证线上确实恢复了
U=https://vibecoding-test-d5fqmhbb955e19dd-1499011319.tcloudbaseapp.com/app
curl -s -H "Cache-Control: no-cache" "$U/index.html" | grep -o '<title>[^<]*</title>'
```

**判据**：标题从坏版本变回 `<title>大学生日程助手</title>`，且三个文件都 200。

### 本次演练的真实记录

| 步骤 | 命令 | 耗时 | 线上结果 |
|---|---|---|---|
| 0 基线 | — | — | `<title>大学生日程助手</title>` |
| 1 发坏版本 | `tcb hosting deploy ./release-archive/_drill-bad app … --safe` | **5,233 ms** | `<title>DRILL-BAD-版本（演练用，故意发坏）</title>` ✅ 坏版本确实生效 |
| 2 回退 | `tcb hosting deploy ./release-archive/v1.0 app … --safe --verify` | **5,289 ms** | `<title>大学生日程助手</title>` ✅ 恢复 |
| 3 校验 | 3 文件 sha256 比对 | — | ✅ **3/3 逐字节一致** |
| — | **全程** | **18,320 ms** | 无坏版本残留（`DRILL-BAD` 计数 0） |

> ⚠ 上表是 2026-10-11 用 **v1.0** 做的演练记录（当时唯一归档）。**2026-10-13 深夜起线上已是 v1.1，回退命令里的版本目录要改成 `v1.1`**（时序：先重传坏版本、再重传正确版本，其余步骤完全不变）。

**结论：这条路真的能用，20 秒内恢复。** 前提只有一个——**你留了归档**。

### 注意事项
- `--safe` 每次都会在 `.cloudbase-backup/<时间戳>/` 留一份被覆盖的版本。**备份不会自动清理**，确认没问题后可手动删旧目录。
- **CDN 缓存**：恢复后若你的浏览器还看到坏的，加 `Cache-Control: no-cache` 或换无痕窗口；CDN 通常几分钟内刷新。
- 如果连 `release-archive/` 都没了，最后一招是 `git log` 找到那次发布的提交，重建 dist（见 §3 末尾）。
- **归档取出后一定要验 sha256**（对照 `docs/发布清单-v1.0.md` §4 的表）。仓库根 `.gitattributes` 里 `release-archive/** -text` 保证归档进库/检出都逐字节原样——**这条别删**，否则本机 `core.autocrlf=true` 会把 LF 换成 CRLF，归档与线上就对不上了。

## 3. Git 回退（代码层）

**铁律**（`AGENTS.md:52`）：用 `git revert`（**保留历史**），**禁止** `git reset --hard`，**禁止**强推。

### 撤掉一个已提交的改动

```bash
git log --oneline -5          # 找到那个坏提交的 short hash
git revert <hash>             # 生成一个「反向提交」，历史不丢
git push origin main
```

- 冲突就手工解决后 `git revert --continue`。
- **不要**用 `git reset --hard <hash>`：它把历史抹掉，一旦推上去别人的仓库就对不上了，而且你的坏改动也没了痕迹，查因无从下手。

### 只想撤「还没提交」的改动

```bash
git status --short            # 看清动了哪些文件
git checkout -- <file>        # 撤单个文件到上次提交的样子
```

### 从历史重建产物（归档丢了时）

```bash
git log --oneline             # 找到 v1.0 那次发布：574a8a3
git worktree add /tmp/rebuild 574a8a3     # 在临时目录检出那次提交（不动当前工作区）
cd /tmp/rebuild/web2 && node ./node_modules/vite/bin/vite.js build
# 把 /tmp/rebuild/web2/dist 当成正确版本，按 §2 传上去
git worktree remove /tmp/rebuild
```

## 4. 云函数回退（本次演练未实操，备查）

**⚠ 本次只写进手册、没有实操**（按 Day 26 口径「云函数回退和数据恢复的实操今日不做」）。

云函数代码在 `cloudfunctions/`，随主仓 git 管理，所以「回退代码」= §3 的 `git revert`。重部署：

```bash
cd D:/Document/Project/vibe-coding-project
tcb fn deploy <函数名> --force        # 如 write / list / sync
tcb deploy --only gateway             # 路由有变化时才要（幂等，不动的会 Skip）
```

**先判断坏在哪一层**：

| 现象 | 可能原因 | 动作 |
|---|---|---|
| 所有请求都 500 | 云函数代码 / 环境变量坏了 | `git revert` 对应提交 → 重部署 |
| 只有写失败 | `WRITE_TOKEN` 环境变量不一致 | 核对 `cloudbaserc.json` 与线上环境变量 |
| 网关 404 | 路由没配 / 配错 | 改 `cloudbaserc.json` 的 `gateway.routes` → `tcb deploy --only gateway` |
| 网关 413 | 请求体超限（网关层就挡了） | 不是云函数的问题，减小请求体 |

**环境变量**在 `cloudbaserc.json`（本机，不入库）与线上 CloudBase 控制台两处，改哪边都要**两边对齐**。

## 5. 数据恢复（本次演练未实操，备查）

**先说最重要的**：云同步（P7）走的是 `sync_docs` 表，每行是**一整份文档快照**（`doc jsonb` + `doc_rev`）。上传是**整份覆盖**，`baseRev` 不匹配会 **409 拒绝**（防误覆盖）——这是第一道保险。

| 场景 | 恢复办法 |
|---|---|
| 误传覆盖了云端 | 本机通常还有原数据（云同步不删本机）；核对后强制上传本机那份 |
| 两台设备互相覆盖 | 旧的 `doc_rev` 还在控制台数据库里（`sync_docs` 表），可手动取回某一行 |
| 本机数据丢了 | 用「设置 → 数据与导入导出 → 导出」的 JSON，或 App 自带的导入功能 |
| 整库误删 | CloudBase 控制台数据库的**备份/回档**（按套餐，本环境为免费档，能力有限） |

**预防 > 恢复**：重要变更前，先在「数据与导入导出」导一份 JSON 存本地。这是最快、最可靠的退路。

## 6. App 回退（本次演练未实操，备查）

```bash
cd D:/Document/Project/vibe-coding-project-app
adb install -r dist-apk/<上一个正常包>.apk     # 若签名相同，就地降级、数据不丢
```

- 包都在壳仓 `dist-apk/` 下归档，按 `schedule-v<版本>-<日期>-debug.apk` 命名。
- **注意**：**同名包每次 ship 都会覆盖**——想要「上一版」，得靠**日期区分**或另外备份，别以为文件名一样就是同一个。
- 换签名（release 包）会**导致数据不兼容**，那条路要按施工单 §R1/R2 的搬家方案走，不是简单 `install -r`。
