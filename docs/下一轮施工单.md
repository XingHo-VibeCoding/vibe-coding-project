### P12 教务直连（登录教务网取课表）

> 用户 2026-10-06 提出：「直接登录教务网获取课表……学校用方正的方案，而且提供了课表导出接口」。这一条同时也把搁置里的「反向导入教务」升级成有具体机制的一条。

- **先分成两半，成本差很远**：
  - **P12a 手动导入增强（小，先做）**：支持把教务导出的文件（Excel / CSV / JSON / HTML）拖进 App → 解析 → **先给预览确认**（「识别到 12 门课，确认导入」）→ 合并进现有课表。**不需要网络层**，先把 80% 的价值吃到。
  - **P12b 原生直连（中）**：在 App 里填账号 → 登录 → 抓课表 → 预览确认。依赖 P12a 的解析层（同一套落库与预览 UI）。
  - **P12c 手动「刷新课表」按钮（小）**：只做手动刷新，**不做定时轮询**（少给人添麻烦，也少撞教务系统的频率限制）。
- **网络这层怎么做（这个仓库的现成条件）**：WebView 里直接 `fetch` 教务网会被 CORS 挡（现在 AI 能裸 `fetch('https://api.deepseek.com/chat/completions')` 是因为 DeepSeek 自己回了 CORS 头，学校服务器基本不会）。两条正路：① 开 Capacitor 7 的 **`CapacitorHttp`**（`capacitor.config` 里 `plugins.CapacitorHttp.enabled = true`，`fetch` 改走原生 OkHttp，不受 CORS 限制）；② 照现有 `Transcriber` / `RecorderService` / `StatusFrameService` 的 **nativePromise 原生插件**写法自己写一个（登录 + 保持 session cookie + 抓导出接口，控制力最强）。**不推荐走云函数代理** —— 账号密码要过服务器，隐私上说不过去。
- **登录形态决定能不能自动化**：纯账号密码最好；**有图形验证码**就把验证码图显示给用户填（不绕过）；**统一身份认证 CAS / 双因子**成本会上去（要跟着跳转链路走）。
- **真正卡住的地方（现在就能确认，比网络那层重要）**：现有课表模型表达不了教务常见的**周次区间**。`web2/src/data/store.js:156-163` 的 `matchWeek(c, weekNo)` 只认 `week_rule = 'every' | 'odd' | 'even'`，所以「1–8 周 / 9–16 周 / 3–15 周」这类任意区间**存不下**；而教务导出的课表基本都带这种区间。⇒ 做 P12b 之前要**先扩模型**（例如加 `weeks: [1..8]` 或 `week_from` / `week_to`），这会触发 `AGENTS.md` 八.1 三份文档同步 + 八.2 旧数据升级方案与「老数据还能正常读」实测。
- **要用户提供才能定实现**（缺这个只能做 P12a 的一半）：① 导出接口地址与请求形态（GET / POST、参数、要不要 cookie）；② **一次脱敏的真实返回**（JSON / Excel / HTML 都行）；③ 登录形态（账号密码？验证码？CAS？）。
- **怎么算过**：导入后课表与教务系统逐条对得上（课程名 / 教师 / 地点 / 星期 / 节次 / 周次）；解析失败**给明确报错且不动本机数据**；断言覆盖「区间周次」与「单双周」两种；预览确认那一步在断言里。
